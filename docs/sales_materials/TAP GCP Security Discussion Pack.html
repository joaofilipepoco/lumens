0 · Overview

Purpose & solution context

Purpose

Structured reference to align with TAP's Cyber Security team on the security posture, tooling, GCP native controls, architecture principles and compliance readiness of the proposed Airline Retail solution on Google Cloud.

Solution in one line

Multi-market airline retail platform: React frontend (GCS + global HTTPS LB) → Cloud Run BFF (Spring Boot) → Apigee → Cloud Run integration services → Pub/Sub / Eventarc → Firestore (eur3) + Memorystore, delivered via GitHub + Cloud Build + Cloud Deploy (Terraform IaC).

Data residency

Persistent serving data held in the European Firestore eur3 multi-region (europe-west1 / europe-west4 read-write, europe-north1 witness). Runtime primarily europe-west1.

Guiding principle

Defense in depth + shift-left: security controls embedded in IaC and CI/CD, enforced at the platform via Org Policy, and continuously monitored - not bolted on afterwards.

Disclaimer

Compliance mappings are indicative to structure the discussion; formal scope (e.g., PCI DSS SAQ vs full RoC, NIS2 entity classification) must be confirmed with TAP's QSA / compliance and legal teams.

3 · Well-Architected — Security

Google Cloud Well-Architected Framework security principles mapped to TAP.

PrincipleWhat it meansHow the TAP solution applies it
Implement security by designBuild security into architecture and IaC from the start, not as an afterthought.Threat modelling per epic; controls codified in Terraform; guardrails via Org Policy before workloads exist.
Implement zero trustNever trust by default; verify identity, device and context for every access; least privilege.IAM least-privilege, Workload Identity (no keys), context-aware access, VPC-SC, private ingress for integration services.
Shift security left (DevSecOps)Embed automated security testing and policy gates throughout CI/CD.SAST/SCA/container/IaC/secret scanning as gates; Binary Authorization; approval-gated Terraform apply.
